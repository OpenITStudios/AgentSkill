# Engineering and Review Methods — Conditional Lenses, Not Eight Executors

**Purpose:** retain proven high-value ideas from existing OpenITStudios engineering rules while avoiding a new orchestrator, duplicate Skills or automatic third-party installation. **Method examples are research patterns**: current task permissions, project architecture and actual evidence always govern their application.

## One compact default engineering pass

Use **Karpathy-style assumption reduction + Ponytail-style preservation review together**, as one short pass:

1. What result is accepted and what assumption could be wrong?
2. Which current semantic owner is responsible?
3. What is the smallest **complete** fix without breaking callers, security, data or tests?
4. What falsifiable proof is available and permitted?
5. Have Standards (correct practice) **and** Specification (requested behavior) both been satisfied at the actual proof ceiling?

Avoid ornate plans or refactors for a straightforward correction. Do not remove quality checks merely because the request is small.

## Optional lenses, explicit triggers

| Lens | Activate only if | Adaptation | Never infer |
| --- | --- | --- | --- |
| Karpathy | any material engineering decision | challenge assumptions, narrow surface, concrete acceptance | authorship endorsement or automatic installed plugin |
| Ponytail | code or contract change | compatibility, affected callers/tests/security in the **same** review | a second mandatory review runtime |
| Pstack/Poteto | material debugging, incident, performance or architecture problem | bounded problem-solving playbook | autopilot, subagents, branches or new router |
| Harness² | agent-method improvement with permission to evaluate | frozen baseline/candidate and comparable evaluation receipts | auto-promotion or test PASS from proposed cases |
| DeepSeek Harness | tool admission, session lifecycle, unreliable tool transport | state/receipt/idempotency principles | replacing the chosen host or enabling preview tools |
| REA | lawful, authorized opaque-system investigation | distinguish direct observations from inferences, record provenance | access to restricted targets or actual analysis tools |
| UI UX Pro Max | actual UI/UX work | accessible interaction, responsive states, existing design-system fidelity | permission to redesign unrelated screens |
| Matt Pocock Skills | domain language/architecture/debug/review ambiguity | precise boundaries, falsifiable hypotheses, two-axis review | all vendor skills installed, extra skill lanes or arbitrary issue tracker |

The first two lenses are **one baseline**; the rest are conditional. Assess relevance cheaply as `APPLY`, `NOT_APPLICABLE` or `UNKNOWN` without opening external repositories. Read only a reference that could materially change a decision.

## Evidence-led problem solving

`EXPECTED → OBSERVED (exact witness) → COMPETING CAUSES → DISCRIMINATING CHECK → FIRST WRONG OWNER → SMALLEST CORRECT FIX → IMPACTED CONSUMERS → MATCHED PROOF`

A tool-ACK, source test written, a green older run, a generated screenshot and a model's self-assessment are different proof classes. An unexecuted discriminating test remains an unresolved hypothesis. Never claim improvements in model intelligence or token efficiency without a comparable measured baseline.

## When spec-driven design is warranted

For cross-system changes or unresolved product meaning, use a compact `requirements → constraints → design boundary → affected contracts → execution units → acceptance` record. Adopt the decision principles of specification-driven workflows, not their entire scaffold. A small bug fix does not require a new constitution, ticket database, task tree, worktree or pipeline.
